## 一、进程管理与调度

### 1. 描述 task_struct 的关键字段，进程和线程在内核里到底有什么区别？（高频，海康二面等）

**要点：**

- `task_struct` 是进程描述符，每个进程/线程都有一个，常驻 slab 缓存。关键字段：`state`（TASK_RUNNING/TASK_INTERRUPTIBLE 等）、`pid`、`tgid`、`mm`（内存描述符，内核线程为 NULL）、`files`（打开的文件表）、`parent`、`prio`、调度类相关字段。
- **Linux 没有真正的"线程"概念**：进程和线程都是 `task_struct`，区别只在**共享什么**。线程是通过 `clone()` 并带上 `CLONE_VM`、`CLONE_FS`、`CLONE_FILES`、`CLONE_SIGHAND` 等标志创建的，共享 `mm_struct`（地址空间）、文件描述符、信号处理，但各有独立的栈和 `task_struct`。
- `pid` 是内核任务 ID，`tgid` 是线程组 ID——`getpid()` 返回的是 `tgid`，所以同一线程组内所有线程 `getpid()` 相同。
- 进阶：多核下进程链表遍历依赖 **RCU** 实现无锁读，保证读者遍历期间任务不会被完全释放。

**考察意图**：是否理解 Linux "轻量级进程"的本质，而非停留在教科书定义。

### 2. fork / vfork / clone 的区别？（高频）

**要点：**

- `fork()`：写时复制（COW）复制父进程地址空间，父子各有独立 `task_struct`；返回 0 给子进程、子进程 PID 给父进程。
- `vfork()`：子进程**共享**父进程地址空间，且父进程被挂起直到子进程 `exec()` 或退出——快但危险（子进程不能随意改栈）。
- `clone()`：最底层系统调用，可精确控制共享哪些资源（内存、FD、信号处理），pthread 就是 `clone(CLONE_THREAD|...)` 实现的。
- 三者最终都走 `kernel_clone()` → `copy_process()`。

### 3. 讲清楚 CFS 的核心思想，为什么用红黑树？nice 值怎么起作用？（必考）

**要点：**

- **CFS（完全公平调度器）**：为每个任务记录 `vruntime`（虚拟运行时间），总是选 `vruntime` 最小的任务运行，长期看实现按权重公平分配 CPU。
- **红黑树**：按 `vruntime` 排序，插入/删除 O(log n)，最左节点是下一个要跑的任务，内核缓存其指针使"取最小"为 O(1)。相比最小堆，红黑树支持高效删除任意节点（任务睡眠/迁移时需要）。
- **nice 值**：映射为权重（nice 0 = 1024，每降一级约 ×1.25，即 nice 越低权重越大）。`vruntime += 实际运行时间 × 1024 / 权重`，权重大的任务 vruntime 涨得慢，获得更多 CPU。
- **追问：CFS 和 EEVDF 的区别？** EEVDF（Earliest Eligible Virtual Deadline First）从 **Linux 6.6 起取代 CFS 成为默认调度器**，引入 lag 和虚拟截止时间，先筛出"有资格"(lag≥0)的任务再选截止时间最早的，把"公平"和"延迟"拆成两个独立维度，解决了 CFS 需要靠启发式规则间接调延迟的问题。能答出 EEVDF 是明显的加分项。

**考察意图**：高级岗要能跟得上内核演进，只背 CFS 已经不够。

### 4. 什么时候触发进程调度？schedule() 在哪执行？

**要点：**

- 触发时机：时钟中断发现时间片耗尽；任务主动阻塞（sleep、等 I/O、等锁）；唤醒了一个应该抢占当前任务的高优先级任务。
- 被动切换通常先设置 `need_resched` 标志，真正的 `schedule()` 在**返回用户态**等安全检查点执行（内核抢占开启时也可在内核态抢占点执行）。

### 5. 实时进程和普通进程的调度区别？什么是优先级反转，内核如何解决？（海康等）

**要点：**

- 实时进程 `SCHED_FIFO`（运行到阻塞或主动让出，无时间片）/`SCHED_RR`（同优先级轮转），优先级 1–99 且高于所有普通进程；只要实时进程可运行，普通进程就得不到 CPU。普通进程走 CFS/EEVDF 按权重公平分配。
- **优先级反转**：高优先级任务等待被低优先级任务持有的锁，而中等优先级任务抢占了低优先级任务，导致高优先级任务实际被中优先级阻塞。
- **解决**：优先级继承（Linux 的 `rt_mutex`/PI futex），低优先级任务持锁期间临时继承高优先级。

## 二、内存管理

### 6. kmalloc 与 vmalloc 的区别？kmalloc 申请 128 字节实际得到多少？（高频，多家）

**要点：**

| 维度 | kmalloc | vmalloc |
|---|---|---|
| 物理内存 | 物理连续 | 物理不连续、虚拟连续 |
| 基于 | slab/slub 分配器 | 伙伴系统逐页分配 + 建页表映射 |
| 大小 | 小内存，有上限（通常 ≤ 数 MB） | 大内存 |
| 性能 | 快，可用于 DMA | 慢（需建映射），不能用于 DMA |

- 申请 128 字节：slub 按固定 size class 分配，实际会落到对应大小的对象缓存（如 128 字节档），通常得到 128 字节对齐的内存块；因 slab 页内布局，可能占用更多物理空间但可用大小按 size class 对齐。答题关键：**按 2 的幂次 size class 对齐分配**，不是按需精确分配。

### 7. 伙伴系统（buddy system）和 slab/slub/slob 分配器的关系与区别？（高频）

**要点：**

- **伙伴系统**：管理**物理页框**，按 2^n 页的阶（order）组织空闲链表，分配大块连续物理内存，通过合并"伙伴"块缓解外部碎片。
- **slab/slub/slob**：建立在伙伴系统之上，面向**内核小对象**。从伙伴系统申请整页，再切分成固定大小对象缓存，减少内部碎片和频繁分配开销。
  - **slab**：原始实现，有 per-CPU 缓存和完整队列，功能全但管理复杂。
  - **slub**：简化版，**Linux 5.x 默认**，每页组织对象、无复杂队列，扩展性好。
  - **slob**：为极小嵌入式设备设计，线性分配，代码小但碎片严重。
- 关键结构：`kmem_cache`、`kmem_cache_cpu`、`struct page`。
- 实操：`cat /proc/slabinfo`、`slabtop` 可观察。

### 8. 虚拟地址到物理地址的转换过程？MMU 工作流程？（高频，嵌入式岗）

**要点：**

- 虚拟地址拆为：页目录号 + 页表号 + 页内偏移（x86-64 为 4/5 级页表）。
- MMU 通过 CR3（x86）/TTBR（ARM）找到页全局目录，逐级查表得到物理页框号（PFN），PFN + 页内偏移 = 物理地址。
- TLB 缓存最近的地址转换结果加速；TLB miss 才走页表；页表项中若"present=0"触发**缺页异常**，由内核 `do_page_fault()` 处理（分配物理页/换入/或 SIGSEGV）。
- 进阶：巨页（hugepage）减少页表层级和 TLB miss；ARM 的 ASID、x86 的 PCID 避免切换进程时刷新 TLB。

### 9. Linux 的 OOM Killer 机制？如何排查和优化？（大厂高频，含云原生岗）

**要点：**

- 触发：所有 zone 水位线不满足、回收/压缩无效时，调用 `oom_kill_process()` 选进程杀死。
- 选杀策略：基于 `oom_score`（0–1000），主要按 RSS 权重，参考 `oom_score_adj`；保护 root/关键进程。
- 排查：`dmesg`/`/var/log/messages` 里查 "Out of memory: Killed process"；确认是谁被杀、谁在吃内存。
- 优化：调整 `vm.overcommit_memory`；用 `oom_score_adj` 保护关键进程；cgroup v2 的 `memory.oom.group` 让 OOM 按组整体杀死，避免留下不一致的 sidecar；用 PSI（Pressure Stall Information）提前预警。
- 进阶：K8s 中 Guaranteed QoS Pod 的 `oom_score_adj=-997`，BestEffort 为 1000——把内核机制和上层编排串起来讲是高级岗亮点。

### 10. 32 位 Linux 虚拟地址空间如何分布？什么是高端内存？（经典题）

**要点：**

- 32 位：0x00000000–0xBFFFFFFF 为用户空间（3GB），0xC0000000–0xFFFFFFFF 为内核空间（1GB）。
- 内核空间前 896MB 直接映射到物理内存（线性映射，`__va()`/`__pa()`），剩余约 128MB 作为**高端内存映射区**，用于映射超过 896MB 的物理内存——因为 1GB 内核虚拟地址不足以线性覆盖全部物理 RAM。
- 高端内存通过永久映射（`kmap`）、临时映射（`kmap_atomic`）等方式动态建立映射。64 位内核地址空间极大，一般不再需要高端内存机制。

### 11. NUMA 架构下内存分配有什么讲究？（大厂进阶）

**要点：**

- NUMA（非一致内存访问）：多 CPU 插槽各有本地内存，访问本地内存快、远程内存慢。
- 内核用 `struct page` 映射物理页帧，按 node + zone 管理；分配时优先从本地 node 分配。
- `zone_reclaim_mode` 控制本地内存不足时是回收本地还是访问远程；`numactl` 可绑定进程到 node。
- 进阶追问会给出"4 个 NUMA 节点的服务器，设计跨节点访问优化方案"的场景题，需结合业务 NUMA 亲和性、中断绑定、内存交错（interleave）来答。

## 三、同步与并发

### 12. 自旋锁和互斥（信号）锁的区别？分别在什么场景用？（必考）

**要点：**

| 维度 | 自旋锁 spinlock | 互斥锁 mutex / 信号量 semaphore |
|---|---|---|
| 等待方式 | 忙等（原地自转） | 睡眠，让出 CPU |
| 上下文 | 可用于中断上下文 | 只能用于进程上下文（会睡眠） |
| 持有时间 | 极短 | 可较长 |
| 开销 | 无上下文切换，持锁久会浪费 CPU | 有上下文切换开销 |

- 核心原则：**中断上下文不能睡眠，只能用自旋锁；可能睡眠的代码绝不能持自旋锁。**

### 13. 中断处理函数中能否使用信号量？为什么中断不能睡眠？（海康等，高频陷阱题）

**要点：**

- 不能。中断上下文**没有对应的 `task_struct`**、不在进程上下文，一旦睡眠无法被调度唤醒，会导致系统死锁/卡死。
- 中断还需快速处理完毕，睡眠会长期占用中断资源。
- 经典翻车现场：在中断处理里误用 `down_interruptible()` 导致内核 panic——能讲出这类实际坑是高级岗加分项。

### 14. spin_lock_irqsave 为什么必须保存中断状态？什么时候用？（进阶）

**要点：**

- `spin_lock_irqsave(&lock, flags)` 先关本地 CPU 中断再拿锁，并把中断状态存进 flags，解锁时 `spin_unlock_irqrestore()` 恢复。
- 使用场景：**同一把锁既在进程上下文又在中断上下文被获取**时。否则：进程持锁 → 中断到来 → 中断里再拿同一把锁 → 自旋死锁。关中断可避免这种自身嵌套死锁。
- 注意它关的是**本地 CPU**中断，多核下其他 CPU 的中断仍可能来，所以才需要自旋。

### 15. 什么是 RCU？读多写少场景如何对比读写锁、RCU、seqlock？（大厂进阶）

**要点：**

- RCU（Read-Copy-Update）：读者无锁读；写者先复制一份修改，然后原子替换指针，**延迟回收**旧数据直到所有已有读者离开临界区（grace period），通过 `call_rcu()`/`synchronize_rcu()` 等待。
- 优势：读性能极高、读者完全不阻塞，适合读多写少（如路由表、进程链表、VFS 数据结构）。
- grace period：所有在替换前开始的读者都结束的时期；`call_rcu()` 注册的回调在其后执行。
- 对比：读写锁读写互斥、写者会阻塞读者；seqlock 读者检测序号变化重试，写者不阻塞读者但读者可能重试多次；RCU 读者零开销但不适合写多。
- 能讲出实测数据（如万节点链表 RCU 读性能数倍于读写锁）是加分项。

### 16. 内存屏障（memory barrier）是什么？为什么下面代码 CPU1 可能打印 0？（大厂经典）

```c
// CPU 0              // CPU 1
data = 123;           while (!flag);
flag = 1;             printk("%d\n", data);
```

**要点：**

- 现代 CPU 和编译器会做**指令重排**和**存储缓冲优化**：CPU0 对 `flag` 的写可能先于 `data` 被其他核观察到，导致 CPU1 看到 flag=1 但 data 仍是旧值 0。
- 编译器屏障：`barrier()`；CPU 内存屏障：`mb()`（全屏障）、`rmb()`、`wmb()`、`smp_mb()` 等；`READ_ONCE()`/`WRITE_ONCE()` 防止编译器优化。
- 正确写法：CPU0 在两写之间加 `smp_wmb()`，CPU1 在读之间加 `smp_rmb()`。
- 与锁的关系：spinlock/mutex 隐含屏障语义；Lockless 编程（如 RCU、无锁队列）必须显式处理。
- 进阶：讲清 Store Buffer、Invalidate Queue、MESI 协议。

### 17. 死锁产生的条件？内核里如何避免和排查？

**要点：**

- 四个必要条件：互斥、请求保持、不可剥夺、循环等待。
- 避免：统一加锁顺序；`lockdep`（Linux 死锁检测机制，运行时检测锁顺序倒置）；`spin_lock_irqsave` 避免中断嵌套死锁；事务性思维。
- 排查：`CONFIG_LOCKDEP`、看 `/proc/lockdep_stats`、hardlockup 检测、利用 `dump_stack()`。

## 四、中断与异常

### 18. 中断上半部和下半部？tasklet 和 workqueue 的区别？（高频，海康等）

**要点：**

- **上半部（硬中断）**：关中断、快速执行、不能睡眠，只做最关键的事（如读寄存器、应答中断）。
- **下半部**：延迟执行耗时任务，可被中断打断。
  - **软中断（softirq）**：静态分配、可在多核并行、性能最高（网络、块设备用）。
  - **tasklet**：基于 softirq，同一 tasklet 不会并行执行，不能睡眠。
  - **workqueue**：运行在进程上下文，**可以睡眠**，适合耗时/需阻塞的任务。
- 对比选择：需睡眠 → workqueue；不需睡眠但要顺序执行 → tasklet；极致性能且可并行 → softirq。

### 19. 中断服务程序中能做什么、不能做什么？

**要点：**

- 不能：睡眠、阻塞、调用可能睡眠的函数（如 `kmalloc(GFP_KERNEL)`、`mutex_lock`、拷贝用户态数据）、访问用户空间。
- 能：用原子操作、`spin_lock`、`kmalloc(GFP_ATOMIC)`、读写硬件寄存器、调度 tasklet/工作队列。
- 根因还是"中断上下文无 task_struct、不可被调度"这一条。

### 20. 如何减少中断延迟？什么是中断线程化？（进阶）

**要点：**

- 中断线程化（`request_threaded_irq`）：把耗时的下半部放到内核线程，给中断线程设置实时优先级，减少硬中断关闭时间。
- `PREEMPT_RT` 实时补丁：将大部分中断处理线程化、自旋锁改为可睡眠的 rt_mutex，显著降低最坏延迟。
- NAPI（网络）：中断 + 轮询结合，高负载下关闭中断改为轮询，避免中断风暴。
- 工具：`cyclictest` 测延迟，`irqstat` 看中断分布，`irqbalance` 做中断亲和性均衡。

## 五、系统调用与内核态/用户态交互

### 21. 用户态调用系统调用时发生了什么？（高频）

**要点：**

- 用户态通过 glibc 封装函数设置系统调用号和参数（x86-64 用 `syscall` 指令，寄存器传参），触发**软中断/陷入指令**陷入内核。
- 保存用户态上下文（寄存器、栈指针、PC）到**内核栈**；切换 CPU 特权级（Ring3→Ring0）和内核页表（页表基址切换，但 TLB 通常保留，靠地址空间隔离）；查 `sys_call_table` 调用服务例程。
- 返回时恢复用户态上下文、切回 Ring3、`sysexit`/`sysret` 返回用户态。
- 用户态栈本身内容不变，只是 CPU 把现场保存到内核栈。

### 22. 用户态和内核态有哪些数据交互方式？如何高效传大块数据？（高频）

**要点：**

- 传统方式：`copy_from_user()`/`copy_to_user()`（会校验用户地址、可能触发缺页）、`get_user`/`put_user`。
- 交互机制：系统调用、`ioctl`、procfs/sysfs、netlink、信号、`mmap` 共享内存、管道/消息队列/socket。
- **大块数据零拷贝**：`mmap`（映射设备内存到用户态）、`sendfile`、`splice`、`get_user_pages()`（GUP，把用户页钉住供 DMA）。
- 进阶：DMA 一致性 —— DMA 缓冲区需 `dma_map_single()` 等做地址映射与 cache 一致性维护；V4L2/DPDK 常用 mmap 零拷贝，答题结合具体驱动案例（如视频 buffer 映射）说服力更强。

### 23. 系统调用、异常处理、中断的区别？

**要点：**

- 系统调用：用户**主动**请求内核服务，同步、陷入指令触发。
- 异常：指令执行出错/特殊情况（缺页、除零、非法指令），同步产生。
- 中断：外设**异步**触发，与当前指令无关。
- 三者都通过中断/异常向量表进入内核，但来源和处理路径不同。

## 六、设备驱动

### 24. 字符设备、块设备、网络设备驱动的区别？（高频）

**要点：**

- **字符设备**：按字节流顺序访问，无缓冲，如串口、键盘。核心结构 `cdev`，`file_operations`（open/read/write/ioctl）。
- **块设备**：按固定大小块随机访问，有缓冲/缓存、请求队列，如磁盘。走 block layer、请求队列、I/O 调度器（mq-deadline、kyber、none）。
- **网络设备**：面向数据包，走 `net_device`、`sk_buff`、NAPI，不通过 `/dev` 节点而是 socket 接口。
- 杂项设备（misc）是字符设备的简化，主设备号固定为 10。

### 25. 驱动加载流程？module_init 为什么会被执行？（经典）

**要点：**

- `insmod` → 系统调用 `init_module` → 加载 ELF  `.ko` 到内核 → 重定位符号 → 执行 `module_init()` 注册的函数。
- `module_init`/`module_exit` 本质是宏，把函数地址放进 `.initcall` 段；内核启动/模块加载时遍历并执行该段的函数。
- 驱动 probe：总线匹配设备与驱动后调用 `probe()`，完成资源申请（ioremap、中断注册、设备创建）；`remove()` 做逆操作。
- `rmmod` 执行 `module_exit()` 清理。
- 追问："驱动第一个执行的函数是什么"——模块是 `module_init` 指定的函数；若是平台驱动匹配流程则是 `probe()`。

### 26. 内核里申请内存的方式有哪些？各自适用场景？（高频）

**要点：**

- `kmalloc`：物理连续小内存，slab 分配，最常用，flag 用 `GFP_KERNEL`（可睡眠）或 `GFP_ATOMIC`（中断中、不睡眠）。
- `vmalloc`：虚拟连续、物理不连续的大内存，较慢，不能 DMA。
- `get_free_pages`/`__get_free_pages`：直接从伙伴系统申请 2^n 页，物理连续。
- `kmem_cache`：为特定对象建专用缓存池（slab 缓存），频繁创建销毁同类对象时高效。
- `dma_alloc_coherent`：申请 DMA 一致性内存。

### 27. 驱动如何实现阻塞 I/O 与非阻塞 I/O？

**要点：**

- 非阻塞：用户 `open` 带 `O_NONBLOCK`，驱动 `read`/`write` 发现无数据立即返回 `-EAGAIN`。
- 阻塞：驱动用**等待队列** `wait_event_interruptible()` 让进程睡眠，数据在中断或另一进程写入时 `wake_up_interruptible()` 唤醒。
- 多路复用：`poll()` 实现，内部用 `poll_wait()` 把进程挂到等待队列并返回可读/可写掩码，支撑 select/poll/epoll。
- 异步通知：`fasync` + 发信号（SIGIO）通知用户态。

### 28. 什么是设备树（dts）？为什么引入？如何调试？

**要点：**

- 设备树描述硬件拓扑（CPU、内存、外设地址、中断号等），把硬件信息从内核代码解耦，同一内核可支持多块板子，通过 DTS（源码）编译成 DTB（二进制）传给内核。
- 驱动通过 `of_*` 系列 API 从设备树节点读取资源；匹配用 `compatible` 属性。
- 调试：`dtc` 反编译 DTB、`/proc/device-tree`、`of_dump`、看 `dmesg` 里设备匹配日志。

### 29. MMIO 访问为什么要 ioremap + ioread/iowrite，不能直接解引用指针？

**要点：**

- 物理地址不能直接被内核虚拟地址空间访问，需 `ioremap()` 建立映射得到虚拟地址。
- MMIO 寄存器访问必须用 `ioread32()`/`iowrite32()` 等，它们内含正确的**内存屏障**和访问语义；直接指针解引用可能被编译器/CPU 重排或缓存，导致设备状态错误。
- 卸载时必须 `iounmap()`。

## 七、文件系统与 VFS

### 30. 什么是 VFS？四大核心对象是什么？（高频）

**要点：**

- VFS（虚拟文件系统）是内核中的抽象层，为 ext4/NFS/proc 等不同文件系统提供统一接口（open/read/write 等）。
- 四大对象：
  - **super_block**：一个已挂载文件系统的元信息。
  - **inode**：一个文件的元数据（大小、权限、时间、数据块指针），**不包含文件名**。
  - **dentry**：目录项，把文件名和 inode 关联起来，dentry cache（dcache）加速路径解析。
  - **file**：一个打开的文件实例，关联进程与 dentry，保存文件偏移、`file_operations`。
- 还有 `vfsmount`（挂载实例）。追问 inode 与 dentry 区别、硬链接/软链接在 VFS 层如何实现（硬链接多个 dentry 指向同一 inode；软链接是存路径字符串的特殊文件）。

### 31. 打开一个文件的完整内核路径？

**要点：**

- `open()` 系统调用 → `do_sys_open()` → `getname()` 拷贝文件名 → `get_unused_fd_flags()` 分配 FD → `do_filp_open()` → `path_openat()` 逐层解析路径（用 dcache 加速，逐级查 dentry/inode）→ 找到或创建 `file` 结构 → `fd_install()` 把 file 装到进程的 fd 表 → 返回 FD。
- 涉及 `file_operations.open` 回调、权限检查、VFS 缓存（dentry cache、inode cache、页缓存）。

### 32. 页缓存（page cache）和缓冲区缓存的作用？writeback 机制？

**要点：**

- page cache 缓存文件数据页，加速读写；读命中直接从内存返回，写先写缓存（write-back）再由内核线程刷回磁盘。
- `address_space` 结构关联 inode 与页缓存。
- 脏页回写：`writeback` 内核线程、balance_dirty_pages、`/proc/sys/vm/dirty_*` 参数调优；`fsync()` 强制刷盘保证持久化。

## 八、网络协议栈

### 33. 一个数据包从网卡到应用程序经过哪些路径？（高频）

**要点：**

- **收包**：NIC 收到包 → DMA 写入内核 ring buffer → 触发硬中断 → 硬中断里 `napi_schedule()` 调度软中断 → 软中断（NET_RX_SOFTIRQ）中 `napi_poll()` 轮询收包 → 构造 `sk_buff` → 协议层处理（链路层 → IP 层 → TCP/UDP，经过 netfilter 钩子）→ 放入 socket 接收队列 → 唤醒应用（`recvfrom`/`epoll`）。
- **发包**：应用 `send()` → socket 层 → TCP/UDP → IP 层（路由、netfilter）→ 邻居子系统（ARP）→ 网络设备层（`qdisc` 排队）→ 驱动 `ndo_start_xmit()` → NIC 发送。
- 关键结构：`sk_buff`（skb）。
- 进阶：NAPI  interrupt mitigation、GRO/LRO/GSO/TSO 卸载、RPS/RSS 多队列、`/proc/net/softnet_stat` 看丢包。

### 34. 软中断和 tasklet 在网络栈里如何用？为什么需要 NAPI？

**要点：**

- 网络收包耗时，硬中断里只做最少的"调度软中断"动作，实际解析放到 NET_RX_SOFTIRQ 软中断。
- **NAPI**：高速收包时中断风暴会压垮 CPU；NAPI 在第一次中断后关闭该设备中断，改为轮询方式批量收包，收完再重新开中断——中断+轮询混合，兼顾低延迟和高吞吐。

### 35. 什么是 netfilter/iptables？5 个 hook 点？

**要点：**

- netfilter 是内核网络协议栈中的钩子框架，iptables/nftables 基于它实现防火墙、NAT、包过滤。
- 5 个 hook：PREROUTING、INPUT、FORWARD、OUTPUT、POSTROUTING。
- 数据包按路径经过不同 hook，每个 hook 上挂若干表的规则链（filter/nat/mangle 等）。

### 36. TIME_WAIT 状态的意义？为什么是 2MSL？（经典网络题）

**要点：**

- 主动关闭方发最后一个 ACK 后进入 TIME_WAIT，持续 2MSL。
- 两个原因：① 保证最后一个 ACK 能到达对端（若丢失，对端重发 FIN，本端还能响应）；② 让本次连接产生的所有报文在网络中消散，避免污染新连接（端口复用）。
- 高并发短连接下 TIME_WAIT 过多会耗尽端口，优化手段：`tcp_tw_reuse`、调整 `ip_local_port_range`、SO_LINGER 等（注意 `tcp_tw_recycle` 在 NAT 环境下有害，高版本已移除）。

## 九、容器虚拟化：namespace 与 cgroup

### 37. namespace 和 cgroup 的区别？（高频，云原生/平台岗必考）

**要点：**

- **一句话核心答案**：**namespace 隔离"能看到什么"，cgroup 限制"能用什么"。**
- namespace 做可见性与身份隔离：PID（容器内 PID 1）、Network（独立网卡/协议栈/端口）、Mount（独立挂载点/rootfs）、UTS（主机名）、IPC、User（UID/GID 映射）、Cgroup、Time。通过 `CLONE_NEW*` 标志 + `clone()`/`unshare()`/`setns()` 创建和进入。
- cgroup 做资源核算、限额与优先级：CPU（`cpu.max`）、内存（`memory.max`）、I/O、进程数（`pids.max`）。
- 容器 = namespace（隔离视图）+ cgroup（资源边界）+ rootfs + capabilities/seccomp/LSM（安全边界）。
- **常见错误答案**：说"cgroup 用于隔离"或"namespace 限制 CPU/内存"——把可见性隔离和资源控制混为一谈是明显的扣分点。
- 进阶：`task_struct.nsproxy` 持有各 namespace 指针；两个进程共享某 namespace 则看到同一视图；cgroup v2 统一层级；rootless 容器靠 user namespace 做 UID 映射。

### 38. 容器与虚拟机的区别？容器的安全边界在哪？

**要点：**

- 容器是**宿主机上的一组进程**，共享宿主机内核；VM 有独立内核，靠硬件虚拟化（VT-x）隔离，边界更强。
- 容器不是"轻量级 VM"——这是面试官重点纠正的说法。
- 安全加固：user namespace UID 映射、精简 capabilities、`no_new_privs`、seccomp-BPF（过滤系统调用）、LSM（AppArmor/SELinux/BPF LSM）、只读/屏蔽挂载、限制设备。
- 特权容器、共享宿主 PID/网络 namespace、挂载 Docker socket 会主动破坏边界。
- 加分：seccomp-BPF 在**系统调用边界**按调用号/寄存器过滤（快但无法安全解引用指针，有 TOCTOU 风险）；BPF LSM（内核 5.7+）挂在内部 `security_*` hooks 上、操作已解析的内核对象，可做更细粒度的 MAC。

## 十、调试、性能与稳定性

### 39. 内核崩了有哪些类型？如何定位 oops / panic？（海康二面等）

**要点：**

- **oops**：内核检测到异常（非法地址、空指针），打印调用栈，可能继续运行；**panic**：严重错误，内核停机。
- 定位：看 `dmesg` 的调用栈和 Oops 信息；用 `addr2line`/`gdb vmlinux` 把地址映射到源码行；配置 `kdump` + `crash` 工具分析 vmcore；`kgdb` 源码级调试；开启 `CONFIG_DEBUG_INFO`。
- 设备初始化失败：`dmesg` 看 probe 错误码、`dts` 是否匹配、`of_*` 取值是否正确。
- 追问"你遇到过内核 panic 吗，怎么定位的"——没有真实经历也要讲清工具链和方法论。

### 40. 常用内核/系统调试和性能分析工具有哪些？

**要点：**

| 类别 | 工具 |
|---|---|
| 系统调用跟踪 | `strace`（用户态）、`ltrace` |
| 内核跟踪 | `ftrace`、`trace-cmd`、`perf`、`bpftrace`/eBPF (BCC) |
| 性能剖析 | `perf top/record/report`、火焰图、`vmstat`、`iostat`、`sar` |
| 内存 | `slabtop`、`/proc/meminfo`、`valgrind`、`kmemleak`、`kasan` |
| 网络 | `tcpdump`、`ss`、`netstat`、`/proc/net/softnet_stat` |
| 死锁/锁竞争 | `lockdep`、`perf lock` |
| 延迟 | `cyclictest`（实时性） |
| 日志 | `dmesg`、`journalctl`、`printk` 级别 |

- 加分：能讲出用某个工具**实际定位过什么问题**（如 perf 火焰图找到热点函数、ftrace 跟踪调度延迟、bpftrace 动态抓内核函数）。

### 41. 内核日志 printk 的级别？如何控制输出？

**要点：**

- 8 个级别（0–7）：KERN_EMERG(0) 到 KERN_DEBUG(7)，数字越小越紧急。
- `/proc/sys/kernel/printk` 四个值控制 console 日志级别；`dmesg -n` 调整；`loglevel=` 启动参数。
- 高频打印要用 `pr_debug`/`dev_dbg` 并在不需要时编译掉，避免拖慢系统。

### 42. 如何给内核增加系统调用 / 编写一个内核模块？

**要点：**

- 加系统调用：在系统调用表（x86-64 `syscall_64.tbl`）注册调用号和入口函数，实现 `SYSCALL_DEFINE*n` 宏定义的函数，重新编译内核；现代更推荐用 `/proc`、`sysfs`、`ioctl` 或 eBPF 而非新增系统调用。
- 内核模块：实现 `module_init`/`module_exit`，用 `Makefile` + `obj-m` 编译成 `.ko`，`insmod`/`modprobe` 加载；模块要声明 `MODULE_LICENSE`（GPL 才能用某些导出符号）。

## 十一、项目深挖类追问（高级岗分水岭）

> 海康二面等大厂明确反馈：**高级岗不问纯八股，而是基于简历项目深挖，验证"你到底做没做过"**。以下追问几乎必现，务必对简历项目逐行吃透。

### 43. 你在项目里负责哪个模块？遇到过什么性能瓶颈，怎么解决的？

**准备方式：**

- 提到"调过性能"必然追问：用了哪些 profiling 工具？数据怎么分析的？优化前后数据对比？

### 44. 驱动出问题你怎么定位？用过哪些工具？

**参考方向：**

- 分层定位：先看 `dmesg`/oops 调用栈 → 确认设备树匹配和 probe 是否成功 → 看中断是否触发（`/proc/interrupts`）→ 用 ftrace/perf 跟踪关键函数 → 必要时 kdump/crash 或 kgdb。
- 结合一个真实的"设备初始化失败/中断不触发/数据异常"案例讲。

### 45. 内核态和用户态交互你怎么实现的？如何保证大块数据一致？

**参考方向：**

- 小数据 `copy_from_user`/`copy_to_user`/`ioctl`；大数据 `mmap` 共享内存 / DMA 缓冲区映射。
- 一致性：锁 + 内存屏障 + 页表写保护；DMA 场景用 `dma_map_*` 维护 cache 一致性。
- 结合具体驱动（如视频采集 V4L2、字符设备）讲。

### 46. 你说做过驱动，probe 函数里具体干了什么？是自己写的还是移植的？

**参考方向：**

- 能说出 probe 里每一步：解析设备树资源（`of_address_to_resource`、`of_irq_get`）、`ioremap`、申请中断 `request_irq`、注册设备（cdev/net_device）、创建 sysfs 节点、初始化硬件寄存器。
- "移植"和"自己写"面试官一听就知道——**实话实说 + 讲清你真正理解的部分**，比硬编更稳。

### 47. 场景设计题（高阶）

- "Linux 下实现一个异步定时器，整点触发" → 内核定时器 `timer_list`/hrtimer + 工作队列。
- "多任务共享资源如何保证线程安全" → 按上下文选锁、避免死锁、原子操作、RCU 场景判断。
- "给一个 4 NUMA 节点服务器，设计跨节点内存访问优化" → NUMA 亲和性、内存绑核、中断亲和、interleave。
- "读多写少的链表，对比读写锁/RCU/seqlock" → 见第 15 题。
